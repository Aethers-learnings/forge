## Verified behavior and current integrity boundaries

`PRAGMA foreign_key_check` examines physical references even when enforcement is
OFF. It reports child table, rowid, parent table and FK index, never row contents.
A composite FK reports its single constraint index; WITHOUT ROWID tables can
report a NULL rowid. `forge_integrity.foreign_key_violations` preserves these
content-free identifiers for internal/test tooling; there is no new endpoint.
Existing migration verification already rejects violations with at most ten
such tuples in the exception. This does not sanitize every SQLite integrity
error or authorize logging user SQL/parameters.

`verify_database` validates reflected schema, ledger order/checksums, SQLite
integrity and FK checks, plus revision-specific invariants, without changing
enforcement. Startup requires managed HEAD and verifies through a separate
read-only SQLite connection before serving (including physical CHECK/index/
trigger/ledger drift). Initialization and explicit baseline/upgrade/downgrade
verify inside explicit write transactions. Downgrades refuse nonempty owned/
blocking tables; frozen history was not edited. Startup is a point-in-time
check: it cannot stop an FK-off application connection introducing an orphan
later. `db-status` is schema/ledger status, not a full integrity gate.

Experiments use independent disposable connections with explicit OFF and ON:

- Fresh migrated schema and valid full-schema fixtures have zero FK violations.
  The fixture satisfies owned membership/sequence and block-event semantic
  verification too. Demo seeding succeeds with FKs ON and remains FK-clean.
- Every one of the 42 physical FK bindings has a populated parent/child fixture.
  ON rejects the referenced parent delete and preserves child fields; OFF allows
  it and FK-check identifies that exact constraint as violated. These graph
  fixtures can have several simultaneous restrictions on a parent; the tests
  also assert each selected physical FK's own orphan metadata under OFF.
- ON rejects a new invalid notification recipient. OFF accepts the same insert;
  content-free diagnostics, migration verifier and read-only startup verifier
  detect it. ORM deletion emits only DELETE FROM user, with no child UPDATE,
  deletion or nulling; final physical rows, not exception presence, prove the bug.
- Enabling FKs inside an already-open `BEGIN IMMEDIATE` transaction is a no-op.
  Settings are per physical connection; a sibling pooled handle and new handles
  remain OFF when just one connection is toggled. Tests reset/dispose their own
  ON handles; the production hook remains WAL/NORMAL only.

## Admin removal: reproduction, remedy and concurrency limit

The old endpoint's `session.delete(user); commit()` succeeds with FKs OFF even
when legacy and owned rows reference the target. It reports “removed” while
leaving those children unchanged and orphaned. No ORM relationship cascade
rescues the assumption. Two maintained regressions failed against that code
before implementation: linked-user preservation and clean-user fail-closed
safety. The raw ORM experiment retains the unsafe old behavior as evidence.

The bounded production seam now uses physical SQLite introspection, including
composite constraints, to check actual user references. It reserves the write
lock with `BEGIN IMMEDIATE`, rechecks active admin authority and admin-target
protection, checks references and commits suspension together. The route releases
its prior ORM read transaction before reserving the independent connection.
It never deletes/nulls children, guesses owners from display names, or returns
private reference metadata. Referenced users receive the compatible generic
“has linked activity — suspended instead” note. Clean users receive the generic
“suspended instead” note. Repeated removal is deterministic; unsuspend works.
Missing users return 404; admin targets 400; non-admins 403; session/CSRF/origin
guards remain. Reservation/preflight/update/commit failures return generic 503,
with rollback and a content-free warning, never a successful-deletion claim.

**Why even clean users suspend:** BEGIN IMMEDIATE excludes competing commits
only until deletion commits. A legacy/application/direct-sqlite FK-off writer
can resolve a valid user before that reservation, wait, and insert the stale
ID after deletion. An independent-connection regression proves a zero-reference
preflight plus locked delete still yields an orphan. Enabling FKs solely on the
removal connection cannot govern that writer. Patching every write route,
adding identity tombstones/triggers, or globally enforcing FKs would exceed this
bounded increment. The authorized fail-closed fallback therefore retains the
user identity even when no current row references it. This is a temporary safety
limitation, not a new permanent retention/deletion policy. Safe hard-delete
convenience remains blocked until the writer boundary is verified separately.

Independent-connection route races exercise both commit orders: child-first
references are retained and the account suspends; removal-first retains the
identity so a stale FK-off insert cannot orphan it. This preserves integrity
without promising that an already-authorized legacy request cannot finish after
suspension; that broader lifecycle authorization issue is separate. Owned-social
writers already re-resolve active actors/peers under BEGIN IMMEDIATE.

Failure injection found SQLAlchemy's commit-event failure may deactivate its
logical transaction marker while SQLite still has an open physical transaction.
The removal seam rolls back both layers explicitly on failure. Tests prove no
child changes, no lost history, no success and no poisoned subsequent request.
If a driver reports failure after an actual commit, the response remains 503;
the only possible persisted target change is non-destructive suspension.

After effective committed suspension, existing Socket.IO room-based retirement
disconnects only target devices in every social mode, including default legacy.
Other accounts stay connected; target reconnect is denied. Delivery remains
best effort and already queued packets cannot be recalled; copied cookies are
not globally revoked. Socket retirement failure produces the existing generic
warning; subsequent authenticated operations still reject suspension.

## Preservation and policy blockers

All 28 direct user-FK bindings are exercised through removal, including optional
owners/viewer/searcher, edge endpoints/requester/recipient/change actor,
endorser/recipient, membership/creator, ownership actor and both block directions/
block actor. Physical snapshots preserve every selected legacy and owned child
field, including messages, memberships, read state, audit and inactive block
history. Nullability never authorizes clearing a reference. Profile-image rows
also prevent removal; suspension retains the existing filename/storage index
and performs no filesystem cleanup. Existing image replacement/explicit image
delete retain their separate storage lifecycle. Display-name posts/comments
do not become inferred user links; an account with only such text is still
classified unreferenced by the FK preflight.

No physical schema defect was found that intrinsically prevents enforcement on
clean migrated databases. This is **not evidence about persistent data**. Likely
orphan classes include any prior FK-off user hard deletion, invalid direct SQL/
fixtures, and parent deletes in operator tooling. NO ACTION is restrictive when
ON, including optional non-NULL owner fields. Performance of unindexed child
lookups can affect deletion checks; correctness does not require changing delete
actions. No destructive or non-destructive schema revision is required here.

Human policy blockers remain exactly the existing separate choices:

- Repair of any discovered persistent orphan where ownership/identity cannot be
  proven: preserve/quarantine and seek an approved mapping/recovery decision;
  never guess, erase or reassign it merely to pass FK-check.
- Permanent account erasure/anonymization, automatic child deletion/nulling,
  CASCADE/SET NULL conversions, legacy cleanup and retention durations need
  D-013 approval. None is necessary to implement suspension safely here.
- T-107 report/evidence retention, erasure/legal hold, notices/appeals, emergency
  access, reviewer provisioning, anonymous reporting, category/rate/evidence
  window policies remain separate. No reports/reviewer tables or roles added.
- Production ownership-v2 cutover still depends on T-107 reporting/reviewers and
  T-201 persistent rollout/recovery. Legacy remains the default; v2 is disabled
  in production. Global FK rollout is a later explicitly reviewed increment.

## Specific next T-201 rollout recommendation (not executed)

Global FK enablement is a suitable **next bounded implementation/rehearsal task**
after this audit is reviewed, with persistent-data reconciliation and explicit
authorization as entry gates. It must not be enabled just by adding a pragma:

1. Operator obtains an authorized consistent backup and works on an isolated
   COPY; record ledger/schema/physical invariants and content-free FK violations.
   This task performs none of those operations on the real database. Require
   zero violations; preserve/quarantine unprovable data and obtain policy approval
   for any destructive repair. Rehearse restore and verify copies before rollout.
2. Configure every newly created application DBAPI connection before any real
   transaction; verify both simultaneous pooled handles and dispose/restart old
   pools. Check the pragma's returned state instead of assuming ON succeeded.
   Do not toggle it inside an existing ORM/service transaction. No per-request
