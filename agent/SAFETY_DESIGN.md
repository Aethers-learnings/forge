# T-107: blocking and reporting design

Status: **CORE SAFETY DESIGN APPROVED on 2026-09-28; implementation outstanding.** The user approved directed blocking with pair-wide interaction denial, relationship cancellation/disconnection and endorsement revocation, retained member-only read-only history, no automatic restoration or cooldown bypass on unblock, authorized-evidence authenticated reports, explicit audited reviewer access without ordinary admin access, and no automatic sanction on submission. Retention, erasure, appeals/notices, emergency access, reviewer provisioning, anonymous reporting, evidence-window size and rate-limit policy remain separate later decisions. The detailed schema/API and validation examples below are implementation proposals where not expressly covered by that approval. This is not an implemented API, migration, moderation permission, or release claim. Read with [OWNERSHIP_DESIGN](OWNERSHIP_DESIGN.md), especially [the target model](OWNERSHIP_DESIGN.md#2-target-model-and-invariants), [capability boundary](OWNERSHIP_DESIGN.md#4-api-and-client-transition--proposed-contract-boundary), [migration stages](OWNERSHIP_DESIGN.md#5-staged-sqlite-migration-and-rollback-plan-not-executable-here), and [D-012–D-016](DECISIONS.md). Existing shared social rows cannot establish participants; never infer a block/report subject from display names or legacy `who`.

## 1. Authority and persistence proposal

| Proposed record | Minimum fields and constraints | Authority |
| --- | --- | --- |
| `user_block` | `blocker_id`, `blocked_id` user FKs, unique directed pair, CHECK unequal, `active`, monotonically increasing `version`, server UTC `created_at/updated_at`, nullable `unblocked_at`; RESTRICT identity deletion | Only the active session user can set their own desired state. Retain the row through unblock for version/race control; no opposite-direction row is created implicitly. Index blocker/active and blocked/active for both-sided eligibility checks. |
| `block_event` | block FK, actor FK, version, previous/next state, UTC time, unique block/version | Append in the same transaction as each effective change; never include message text. Only security operators with an explicit operational need see this log. |
| `safety_report` | opaque public ID, reporter FK, subject user FK, one typed evidence reference (`user`, owned edge/request, conversation, message sequence, or visible profile/content object), category, bounded optional comment, private state, timestamps, optional submission UUID unique per reporter | Server derives reporter and subject from authenticated authorized evidence, never from a supplied reporter/subject ID. RESTRICT evidence references or use a verified immutable typed reference with integrity checks; no copied conversation history. Index reporter/time and state/time, never offer a public subject report count. |
| `report_event` and `report_evidence_access` | report FK, authorized reviewer FK, transition/action or evidence-reference access, reason, timestamp; append-only with uniqueness for retried transitions | Every review, view of sensitive evidence, disposition and access denial requiring audit has an attributable actor and purpose. No report content or message text in general logs, sockets or notifications. |

Use the existing SQLite migration ledger and backup/restore process from T-201. Enforce pair uniqueness, directed identity, FK integrity, bounded state/category values and event uniqueness in the database where possible; transaction services enforce authorization and cross-table eligibility. `PRAGMA foreign_keys=ON` needs the whole-schema review in D-015. No blanket admin conversation read route follows from these records.

**Approved core behavior:** a block makes the pair's current `network_edge` terminal `disconnected` (pending becomes `cancelled`), revokes both directions of active endorsements, and leaves any `direct_conversation`, authored messages, per-member read cursors and history intact. This uses the existing consent lifecycle and its `ownership_event` audit, rather than maintaining an accepted edge that appears usable. A block transaction serializes against edge transitions/sends, increments affected versions, and records the block and edge/endorsement events atomically. No block reason is stored in the public edge event. The end state shown to either peer is generic; the blocker alone may see their own block control/state. If no edge exists, the block still prevents contact. Unblocking changes only the directed block record: no request, accepted edge, endorsement, unread state, queued notification or sending permission is restored. A fresh explicit request follows the accepted 24-hour terminal cooldown and normal eligibility checks; it never bypasses another active block. A former blocker has no cooldown exception.

## 2. Pair-wide enforcement and privacy

Treat **either** active directed block as a pair-wide interaction denial. The server checks both directions inside the same serialized write transaction as a new request, re-request, acceptance, thread creation, send, or endorsement activation. A first block and a concurrent acceptance/send have a defined commit order: an earlier committed action remains historical; any action authorized after block commit fails without side effects. A read-only history fetch and explicit own read-cursor advance remain possible for an authenticated existing member even after block/disconnect, subject to account suspension and future approved retention policy. Reporting retained evidence remains possible. An account without prior membership never gains history from a block or report.

| Surface | Effect while either direction is blocked |
| --- | --- |
| Suggestions, discovery and profile-mediated social entry | Exclude pair before sorting, counts, cursors and pagination. Ordinary public-profile visibility outside social discovery needs a separate product decision; no block list or blocker identity is exposed to the other user. |
| Pending/accepted edges | Block atomically cancels pending or disconnects accepted state. No opposite request, accept, re-request or reconnection while blocked. Generic ended/unavailable projection; no block-specific status or timestamp visible to peer. |
| Existing conversation | Keep member-only history and read cursors. No new conversation or send; UI shows generic read-only state without stating which person blocked. Existing sent content is not recalled. |
| Endorsements | Revoke active endorsements in both directions in block transaction. Suppress blocked pair from reputation/relationship projections. No automatic reactivation on unblock. |
| Notifications and sockets | Do not create contact notifications for a denied mutation. Suppress undelivered social notifications and unread counts/links that would reveal new contact across the pair; historical generic notifications require a policy decision before deletion. Emit only minimal generic invalidations to active authorized user rooms after commit, with no block actor/reason/message text; never broadcast to role rooms. Recheck pair eligibility, membership and active sessions immediately before delivery. A packet already queued/delivered cannot be recalled. HTTP refresh always reauthorizes. |

The blocker may list only their own active blocks with limited peer display needed for unblock; the blocked peer has no block-list endpoint. For a peer with a known edge, denied interactions use the same generic 409 `operation unavailable` as other unavailable relationships; hidden/nonexistent targets and nonmembers receive the same concealed 404 shape as ownership v2. Do not expose block-specific headers, messages, sorting, counts, timing-dependent existence checks, socket events or notification previews. Exact latency equality is not promised; rate-limit probing. A suspended actor receives 403 and a missing/deleted actor 401 per existing login guard. Suspension of the peer denies new contact without deleting either block; authorized existing members retain read-only history. On deletion, RESTRICT references and the approved admin-removal fallback must preserve records until a separate erasure policy is approved. Suspension/deletion disconnects affected sockets as in D-014; an old copied signed cookie is not globally revoked by this design.

## 3. Reporting and reviewer boundary

An active user may report another visible user/profile, a request/edge in which they are an endpoint, a conversation in which they are a member, or a message sequence they can read in that conversation. Reporting stays available after block/disconnect for such retained evidence; do not require an accepted current edge. A generic user report requires the target to be legitimately observable under existing profile visibility rules or to have an authorized prior pair context. Profile/content reports require the same visibility the reporter had at submission; a later change cannot grant new evidence access. A user cannot report themselves. The server verifies typed ID, membership/visibility and derived subject before creating the report; a foreign/missing reference has an identical concealed 404 and no report row. For deleted/hidden evidence, retain a minimal verified reference only if the reporter was eligible and policy permits; never manufacture a subject from ownerless legacy rows.

**Proposed validation:** category from a fixed allowlist (`harassment`, `spam`, `impersonation`, `safety`, `other`); optional trimmed comment at most 1,000 Unicode code points, no blank-only comment, no URL fetch/attachment upload, and no client-supplied message quote or bulk conversation snapshot. Client-generated UUID `submissionId` is unique per reporter: identical normalized target/category/comment returns the original generic acknowledgement on retry, changed payload with the same key returns 409. A second distinct report may be legitimate, but cap duplicate submissions per reporter/target/category over a policy-defined window and rate-limit per account/IP without revealing prior reports. Return the same generic receipt regardless of whether a reviewer later acts; submit does not automatically sanction the reported user. **Requires human approval:** category taxonomy, duplicate window/rate thresholds and whether anonymous safety reporting is needed; anonymous reports are outside this proposed authenticated API.

Proposed states are `submitted → triaged → closed` or `triaged → escalated → closed`; a closed report may be reopened by an authorized reviewer with an audited reason. Only a specifically assigned reviewer role/grant may list or transition reports; ordinary `admin` and report subject get no implicit access. Reviewer assignment and separation of duties require explicit approval before implementation. Reporter gets their own receipt and coarse state (`received`/`closed`) without reviewer identity, evidence from other users or sanctions. The reported user does not see reporter identity, report existence, details, counts or appeal status via this API. **Requires human approval:** notice, appeal and reporter-feedback policy; do not imply that closure means a penalty or create an automatic ban.

Reviewer list/detail initially contains report metadata, category, reporter reference only as necessary, and a redacted evidence descriptor. For a message report, a specifically authorized reviewer can request only the cited message and minimal necessary thread context through a dedicated audited evidence operation, after assignment and a recorded purpose; ordinary conversation endpoints remain participant-only even for admin. No broad search, arbitrary thread pagination, export, or access to unrelated messages. Every access records reviewer/report/evidence range/purpose/time; access is denied after assignment removal and logged without leaking contents. **Requires human approval:** reviewer grant authority, maximum contextual window, emergency access, retention periods, legal hold, erasure/anonymization, audit visibility and storage of evidence when a message is later edited/deleted. Until decided, preserve referenced records under RESTRICT; do not promise permanent retention or irreversible cleanup. Private report data is excluded from generic analytics, logs, user notifications and existing profile export pending a separate export/erasure decision.

## 4. Proposed API and client contract

All paths here are **future** paths, require an active session and `X-Forge-Ownership-Version: 2`, and inherit D-014's 426 update response. Unsafe methods require same-origin Origin/Referer and `X-CSRF-Token`. Apply auth/CSRF/capability before object lookup; then authorization before object-dependent validation. JSON errors follow [API_CONTRACT](API_CONTRACT.md); use `Cache-Control: no-store` on private responses. Reject actor/reporter/subject/role/room fields (400 once object authorization is established). A version header never authorizes access.

| Method / path | Request and response | Failure/authorization |
| --- | --- | --- |
| `GET /api/network/blocks` | Own active blocks, bounded 50, user-scoped cursor, limited peer label/ID and version; no foreign direction or aggregate | 401/403 session; malformed cursor 400; never expose who blocked caller |
| `PUT /api/network/blocks/:targetUserId` | `{blocked:true|false, expectedVersion}`; 200 `{ok:true, blocked, version}` for existing state, 201 on first create | Self/hidden/nonexistent target concealed 404 except an existing own block remains manageable; missing precondition 428, stale change 409; peer's block state never returned |
| `POST /api/safety/reports` | `{kind, referenceId, messageSequence?, category, comment?, submissionId}`; 202 `{ok:true, receiptId, status:"received"}` with stable retry receipt | Invalid syntax/limits 400 after authorization; foreign/missing evidence 404; changed same-key payload 409; throttling 429 with generic retry guidance |
| `GET /api/safety/reports/:receiptId` | Reporter-only coarse receipt `{receiptId,status}` | Other reporter/nonexistent both 404; no reviewer details or reported-user view |
| `GET /api/reviewer/reports`, `GET /api/reviewer/reports/:id` | Explicit reviewer grant only; bounded queue and redacted metadata | 403 for ordinary admin/nonreviewer, 404 for unauthorized report; no conversation data |
| `POST /api/reviewer/reports/:id/evidence` | `{purpose, expectedVersion}`; audited narrow evidence projection | Assigned reviewer only; no arbitrary message ID/range; 403/404/409 as appropriate |
| `POST /api/reviewer/reports/:id/transition` | `{action, reason, expectedVersion}`; 200 state/version after atomic audit | Assigned reviewer only; 428 absent, 409 stale/invalid transition; no automatic account sanction |

The exact reviewer grant provisioning and rate-control infrastructure remain separate later decisions. The approved access boundary is not a reason to reuse the current broad admin list privilege. Reviewer API must remain gated/unavailable until grants, audit and retention policy are approved. If a block is deactivated, require the own existing block ID/target to remain addressable even when the peer has hidden their profile; a stranger cannot use that exception to enumerate users.

Web and WebView need keyboard/touch-accessible block/unblock controls on eligible profile/relationship views, confirmation for a block that ends the connection, an accessible report dialog with category/comment limits and a generic receipt. Set busy state against double submit; provide nonrevealing 401/403/404/409/426/428/429/503 guidance, retry the same submission UUID, reload stale versions without replaying intent, and clear account-scoped receipts, blocks, lists and pending actions on logout/switch. Drop late fetch/socket results using the current account generation; close socket on logout. A cached page cannot bypass server denial. Any released native social screen must implement equivalent controls and account isolation with its own verified session/CSRF flow; do not assume WebView cookies and native `fetch` share authentication. Existing native social screens do not yet exist.

## 5. Migration, rollback and executable future evidence

After T-201's baseline/integrity work, add only reviewed tables/indexes with legacy rows quarantined under D-013. No block/report import from ownerless NPC records. Rehearse clean/populated SQLite migration and repeated version checks, FK/orphan rejection, unique directed pairs, event version integrity, backup restore and admin removal behavior. Gate social writes until both ownership and safety services/clients pass together. Before new writes, a compatible gated release is reversible; after writes, rollback uses a secure compatible release or maintenance 503 while preserving blocks, reports, audit, new messages and cursors. Never restore an older snapshot over new reports or expose legacy social state. Reconcile/report recovery in an isolated copy; policy-controlled erasure is separate.

Future test fixtures use active A/B/C and separately authorized reviewer R plus ordinary admin D; distinct sessions, CSRF tokens, matching display names, independent SQLite connections and Socket.IO clients. These are requirements for later implementation, **not tests added or passing in this design PR**.

| Test group | Required assertion |
| --- | --- |
| Identity/isolation | A blocks B; C and B cannot list/change A's block. Forged blocker/reporter/role fields, IDs, cookies/CSRF and foreign report references fail without writes. D cannot read reports/evidence by being admin; assigned R can inspect only its report with an audit row. |
| Pair state/privacy | A→B pending and accepted cases: block cancels/disconnects and revokes endorsements in both directions; B→A block independently works. Neither side sees block actor/reason/count in errors, suggestions, cursors, sockets, analytics or notification previews. Unblock never restores a request, edge or endorsement; explicit cooldown/re-request applies. |
| History/reportability | A/B retain only their own read-only history and own read cursors; C/R cannot use ordinary conversation routes. A/B may report authorized past message after block/disconnect; foreign message sequence, hidden profile and ownerless legacy row reveal no evidence. Narrow assigned R evidence access logs purpose and exact scope; removed grant denies future access. |
| Races/retries | Synchronize block against accept, opposite request, create, send, endorse, read and delivery on independent connections. Commit order yields no post-block contact; prior committed message remains; retry same block/report key has one effective event/receipt, stale versions conflict. Inject rollback and post-commit emission failure; no phantom notification or duplicate report. |
| Account lifecycle | Suspended/deleted actor cannot mutate or socket rejoin; peer suspension preserves active blocks and report history but denies new contact. Referenced deletion fails safely without cascading evidence. Already queued minimal packets cannot be recalled; subsequent fetch and delivery reauthorize. |
| Migration/clients | Clean and legacy-populated DBs keep quarantine, block/report rows and audit across migration/secure rollback. Stale web/WebView, native separate sessions, logout/account switch, offline retry, old IDs, keyboard/screen-reader state and no-store/CSRF/capability errors are exercised. |

Record implementation test results, remaining policy decisions and signed-device checks before marking T-107 implementation complete or claiming social production readiness.
